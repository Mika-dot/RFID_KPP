## Два временных окна

`common/adaptive_windows.py` оценивает задержку между физическим RFID-событием
КПП и регистрацией склада. Группы: транспорт, сезон, время суток, день недели;
при недостатке данных применяется более общая группа. Минимум 8 примеров,
устойчивые квантили и запас 30 секунд. Это общая задержка: время движения
погрузчика отдельно от ожидания/регистрации без дополнительных timestamps
не измеряется.

Первое окно — ожидаемый проход, отсчитанный назад от склада. Второе —
ретроспективный поиск до 7 суток. Читаются реальные raw rows с точным EPC+TID;
сохраняются до 200 кандидатов, антенны/RSSI/время и выход за старое окно.
Raw-кандидаты — диагностика, а не автоматически подтверждённый новый проход.
Штатный sessionizer восстанавливает сессии в порядке raw Id; диагностика
показывает направление, границы, read/antenna counts, задержку и time-fit score.
Обрезанная выборка помечается; score не называется вероятностью или доказательством.
Связать существующее KPP-событие можно только при `RfidReadCount>0`.
Warehouse-only не доказывает работу считывателя.

| Режим | Поведение |
|---|---|
| Выключено / `off` | Прежняя обработка |
| `shadow` | Модель и ретроспективная диагностика; рабочее окно остаётся прежним |
| `active` | Отдельный принятый профиль; непринятый/повреждённый файл блокирует запуск |

Shadow обучается на уже связанных реальных RFID-событиях с Warehouse по TAG/IDS,
без IN/conflict и без adaptive-match. Adaptive links исключаются из будущего
обучения, чтобы модель не подтверждала собственные ошибки. SQL-набор ограничен,
скользящий за 180 дней; обновление раз в 15 минут. Эти связи дают кандидат
распределения; независимая разметка оператора нужна для принятия active.

Градиентный спуск выполняется offline на JSON-массиве размеченных пар:
`label` (`confirmed` / `rejected`), `event_id`, `warehouse_id`, `kpp_at`,
`warehouse_at`, необязательный `transport`. Дубли запрещены. Разделение по
времени 70/30; positive/negative нужны и в train, и в holdout. Принятие:
recall ≥ max(0.95, legacy recall), false-positive rate ≤ min(0.05, legacy FPR).
В отчёте метрики/размеры групп/SHA-256 модели и входа.

```bash
python deploy/ha/tune_adaptive_windows.py --input labelled-pairs.json --output accepted-windows.json
```

Настройки: `resilience.environment.example`. Active по умолчанию выключен.
Реальные заводские пары в этой сессии не размечены, прирост precision/recall
не измерен. Сезонный дрейф требует нового проверенного профиля; принятый профиль
не изменяется автоматически собственными предположениями модели.

## Локальные копии и доставка

Подготовщик конфигурации включает `fallback_enabled=true`,
`fallback_retention_days=93`. Минимум 93 дня покрывает три календарных месяца.

| Файл в прежнем state_dir | Назначение |
|---|---|
| fallback.sqlite | UUID-журнал метаданных RFID/YOLO без фото; PENDING не удаляется по сроку |
| metadata.sqlite | SELECT-only зеркало шести потоков: события КПП, Warehouse, 1C tasks, raw RFID, video metadata, СКУД |
| Прежние spools и replica.sqlite | Полные недоставленные входы, штатная idempotent доставка через SQL-owner |

Метаданные сохраняются на отправителе и принимающих репликах до ACK. После SQL
commit архив становится COMMITTED, затем исходный spool SENT. Ошибка архива
оставляет spool для повтора; UUID не допускает повторной SQL-вставки.
Зеркало обновляется bounded-пакетами по 500 строк раз в минуту, с атомарным
checkpoint. Warehouse/1C идут по Id и предполагают неизменность импортированных
строк; raw RFID/video/СКУД также идут по исходному Id. Фото и персональные поля
СКУД не зеркалируются. Откат primary/исчезновение anchor выдаёт ошибку, не сбрасывает локальную
историю и не помечает её свежей. Возраст/размер/очереди публикуются в мониторинг.

Готовность копии требует всех шести caught-up потоков не старше 130 секунд и
минимума 93 дня configured retention. Незавершённый backfill показывается как
заполнение. GET-only installation verifier с `--require-local-copies` проверяет
это на каждом узле, плюс архив и резервный просмотр. Выбор копии предпочитает
свежую исправную полной; более новая ошибка не вытесняет рабочее зеркало.

Это компактная копия метаданных, **не полный SQL Server backup**. Автоматический
replay PENDING идёт через прежние spools/реплики. Callback replay архива не
является восстановлением полностью уничтоженной БД: нужны штатные SQL backups,
reconciliation и отдельная процедура восстановления.

При полном отказе SQL authority workers останавливаются существующим fencing.
Непрерывный захват при таком отказе требует SQL HA listener/control storage;
это инфраструктурный этап, ещё не выполненный. Код не разрешает несколько
offline лидеров. VM/диски на одном хосте не дают независимых failure domains.

## Постоянный Web

Gateway — отдельный сервис Comparator :5051; выбирает Web действующего SQL-owner.
Предложенный `http://172.31.0.192:5051` ещё не принят инфраструктурой. Обычный IP
physical/perimetr в public_url запрещён. При отказе primary/owner GET показывает
авторизованную свежую или явно устаревшую копию; POST offline-записи не выполняет.
Fallback использует существующие `KPP_WEB_AUTH_USER` / `KPP_WEB_AUTH_PASSWORD` из
закрытого environment; без них доступ закрыт. Liveness не зависит от SQL,
readiness подтверждает owner.

Отказ physical не останавливает отдельный gateway. Для отказа самого Comparator
нужен независимый proxy/VIP/DNS и сетевой fencing; одного gateway недостаточно.

## Grafana: две страницы

Grafana `http://172.31.0.97:3000`. Сохраняются общий UID
`mositlab-director-wallboard`, Infinity `wallboard-api`, Business Charts и
остальные проекты. Новая страница `mositlab-perimeter-visual`:

- состояние/ведущий/резервы, въезд/выезд/только склад за 24 часа;
- источники, три узла, все 15 workers, SQL/controller, окна, очереди/копии/Web;
- активные стрелки: зелёная цепочка, голубой резерв, жёлтое предупреждение,
  красный отказ, серое отсутствие данных;
- таблица очередей/копий/SHA по всем узлам и последние проходы.

Старые данные и несколько ведущих не рисуют зелёную действующую цепочку.
Warehouse-only отдельно от RFID-выезда. Repair verification/update trial/quarantine
и readiness RTO показываются из фактических наблюдений; это не LLM readiness
или физический business RTO. Без наблюдений серое состояние. Последние записи берутся из нового
зеркала; до его установки/заполнения показывается отсутствие данных.
Refresh 5 секунд; playlist переключает общий экран и Периметр каждые 1 минуту.
