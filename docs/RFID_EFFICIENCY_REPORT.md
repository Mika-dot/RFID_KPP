# Стандарт отчёта эффективности КПП «Периметр»

Версия 1.1, формат от 23.10.2026. Это основной стандарт
периодического управленческого отчёта. Не возвращать в него все диагностические
листы прежней ручной сверки.

## Как пользоваться

На основном сайте `http://172.31.0.97:5051/` открыть **«Отчёт эффективности»**,
выбрать **«Дата от»** и **«Дата до (включительно)»**, нажать **«Сформировать
отчёт»**. После завершения доступны предпросмотр, **«Скачать Excel»** и
**«Скопировать письмо»**. Письмо копируется с таблицами, в том числе на
существующем HTTP Gateway; при запрете браузером доступен обычный текст.
Письмо автоматически никуда не отправляется.

Состав по умолчанию — один лист **«Отчёт»**:

1. Название и выбранный период, время МСК.
2. Два главных показателя: **«Периметр целиком»**, затем **«RFID-блок»**.
   Рядом с процентом всегда указаны числитель и знаменатель.
3. Таблица по дням и строка «Итого»:
   `Дата | Всего барабанов | С RFID | RFID считано | RFID KPI | Периметр целиком`.
4. Краткое объяснение учёта барабанов без зарегистрированной RFID-метки.
5. Количество барабанов с зарегистрированными метками без подтверждённого
   считывания. Список серий и технические причины — на опциональном листе сверки.
6. Готовый текст письма с темой, приветствием «Добрый день, Павел Валерьевич!»,
   двумя главными показателями в начале, актуальными таблицами, объяснением и выводом. Не обещать будущую проверку,
   которую система сама не выполняет.
7. Короткая методика и время формирования для воспроизводимости результата.

По отдельной галочке добавляется **один** лист **«Сверка»**: серия, время и ID
приёмки, наличие меток 1С, подтверждение считывания, полные метки, ID событий,
неоднозначные привязки. Для Reader дополнительно указаны ID исходных чтений,
их время и полная метка; отдельно видно наличие подтверждения у Aggregator.
Полный поток сырых RFID-чтений, видео, фотографии, все записи 1С,
все события сайта, повторы и дополнительные серии вне складской выборки
в стандартный файл не включаются.

Оформление следует приложенному образцу: светлый фон, Carlito, тёмно-синий
заголовок `#16364D`, светло-синие шапки `#DFE8EF`, перенос длинного текста,
выделенная итоговая строка. Числа остаются числами; дневной и общий RFID KPI
и общие количества рассчитаны формулами с сохранёнными значениями. Нулевой
знаменатель — пустая процентная ячейка в Excel и «—» в предпросмотре/письме.

## Правила расчёта

**Эталон выборки — прямые записи адресного склада `dbo.Warehouse`** за период
`[начало первого дня; начало дня после последнего)`, а не количество строк
на экране сайта. Используются все строки, без лимитов пагинации Web.
Серия приводится к верхнему регистру, удаляются пробелы по краям и конечные
запятые/точки с запятой/точки (`4265/26,` → `4265/26`, `8975/26.` → `8975/26`). Разные непустые серии
не склеиваются, пустая серия вызывает ошибку, а не молчаливое исключение.

Единица отчёта — **уникальная серия барабана за выбранный период**.
Повторные строки склада и несколько меток одной серии не увеличивают число
барабанов. Дата — первая приёмка серии в периоде. Это отчёт о барабанах,
а не о количестве перемещений одной серии. Повторные приёмки одной серии
за другой период учитываются в соответствующем отчёте заново.

Серии с суффиксом `МК`/`MK` исключаются, как в согласованной сверке. В текущей
таблице Warehouse нет вида тары: отнесение остальных серий к барабанам
опирается на принятую номенклатуру учёта. Если в этот поток начнут поступать
бухты без отличимого суффикса, сначала нужен явный признак тары в источнике;
нельзя заявлять, что имеющиеся пять полей позволяют определить её физический вид.

| Колонка | Определение |
|---|---|
| Всего барабанов | Число уникальных серий складской выборки |
| С RFID | У серии есть хотя бы один непустой полный Tag в `dbo.RfidTags`, зарегистрированный не позже первой приёмки |
| RFID считано | Хотя бы один зарегистрированный полный Tag точно совпал с исходным чтением Reader в окне приёмки или с физическим RFID-событием КПП |
| RFID KPI | `RFID считано / С RFID`; итог считается из сумм, а не как среднее дневных процентов |
| Периметр целиком | Число складских серий в объединённом учёте Периметра / всего складских серий |

Полный Tag — EPC вместе с TID, как в `RfidTags.Tag` и `KPP_ReelEvents.SourceTag`.
Совпадение только EPC-префикса недостаточно. Пробельное оформление полного
кода и регистр нормализуются. Несколько разных зарегистрированных меток одной
серии допустимы: достаточно одной считанной. Метка, зарегистрированная за
несколькими сериями, не доказывает обнаружение; это явно отмечается в отчёте.

**История реестра меток читается целиком до конца периода**. Не применять к
ней окно ±24 часа или 72-часовой cache агрегатора: регистрация может быть
за несколько месяцев до фактической приёмки. Метки, зарегистрированные после
приёмки, не увеличивают её исторический знаменатель.

Подтверждение RFID берётся из **двух источников**: исходного журнала
`dbo.RFID_Tags` (Reader) и `dbo.KPP_ReelEvents` при `RfidReadCount > 0`
(Aggregator). Отсутствие связанного события Aggregator само по себе не означает,
что Reader не прочитал метку. Показатель только по Aggregator не подменяет
основной KPI RFID-блока. Итоговая доля считается по объединению физических
подтверждений, с дедупликацией серии и полных меток.

Чтения Reader сопоставляются по точному нормализованному `EPC+TID` с меткой
реестра, в пределах ±24 ч от складской приёмки. SQL возвращает ограниченные
агрегаты по приёмке и метке: число чтений, первое/последнее время, min/max ID
реальных исходных строк. Время и идентичность повторно проверяются в расчётном
модуле. Несколько окон одной серии не увеличивают количество барабанов.

`WAREHOUSE_ONLY` и `SUPERSEDED_BY_KPP` не являются подтверждением физического
считывания, даже если в строку скопирован Tag из 1С. Само присутствие серии
на сайте и наличие Warehouse-записи не доказывают чтение антеннами.

Сопоставление с приёмкой:

1. Сохранённый `WarehouseId` — приоритетный, в том числе при задержке больше
   суток. Tag всё равно обязан совпадать с реестром этой серии.
2. Для ещё не связанного события — точный полный Tag из реестра серии в
   пределах ±24 ч от приёмки, с исключением известного возврата `IN`.
3. Событие, уже связанное с другой Warehouse-записью, не перехватывается.

Это отдельная отчётная проекция, а не изменение алгоритма идентификации
агрегатора `TAG → IDS → однозначный SERIES`. Исторические метки одной серии
не должны искусственно превращаться в «неоднозначную серию» для этого KPI.

`Периметр целиком` включает прямые Warehouse-записи по существующему
контракту `RFID КПП ∪ адресный склад`. Поэтому при доступном и полном чтении
складской выборки этот показатель равен 100%; он не является независимой
проверкой антенн или полноты внешнего обмена 1С со складской SQL-таблицей.

Регистрация в 1С не гарантирует, что физическая метка сохранилась на барабане.
Стандартная формулировка расхождения: «считывание не подтверждено у барабана
с зарегистрированной меткой», а не безусловное «антенна неисправна».

## История контрольного примера и границы проверки

Исходная ручная сверка 19–22.10.2026 содержала следующие значения:

| Дата | Всего | С RFID | Считано | RFID KPI | Периметр целиком |
|---|---:|---:|---:|---:|---:|
| 19.10 | 24 | 1 | 0 | 0% | 24/24 |
| 20.10 | 34 | 24 | 24 | 100% | 34/34 |
| 21.10 | 40 | 24 | 24 | 100% | 40/40 |
| 22.10 | 33 | 32 | 32 | 100% | 33/33 |
| Итого | 131 | 81 | 80 | 98,77% | 131/131 = 100% |

Эти числа являются историей ручной сверки, **а не доказанным эталоном физической
работы Reader**: старый экспорт проходов мог помещать Tag из 1С в Warehouse-only
строку с нулевым RfidReadCount. Поэтому воспроизведение этих чисел из прежнего
Excel проверяло арифметику и сопоставление меток, но не физическое считывание.
Нельзя подставлять 98,77% в новый отчёт как константу или исключать серии ради
достижения этого процента.

Новая заводская выгрузка v1.0 содержала 134/83/36; она читала только события
Aggregator и не проверяла исходный журнал Reader. Эти 43,37% также нельзя
автоматически считать окончательной эффективностью RFID-блока. В новой выборке
есть дополнительные серии 8843/26, 8844/26, 8652/26; их наличие требует сверки
складских источников, а не жёсткого исключения из кода. 4265/26 в новой выгрузке
имеет подтверждение событием 75074, в отличие от прежней ручной сверки.

Синтетические регрессии проверяют оба исхода: 36 серий у Aggregator плюс 44
дополнительных подтверждения Reader дают 80/81 = 98,77%; если исходных чтений
нет, результат не завышается. Реальные показатели рассчитываются только после
полного успешного чтения обоих источников. Реальные EPC в тестах не публикуются.

## Источники, сервер и границы

- Реализация: `common/efficiency_report.py` — единая расчётная логика и письмо;
  `common/efficiency_xlsx.py` — Excel; `web/efficiency_api.py` — SQL и задания;
  `web/efficiency_ui.py` — диалог. Подключение — production wrapper
  `web/kpp_reel_dashboard_v3_fixed.py`. Старая выгрузка проходов сохранена.
- Warehouse и RfidTags читаются через существующий `KPP_TASK_CONN_STR`, если
  он задан; иначе через `KPP_WEB_DB_CONNECTION`/`RFID_DB_CONNECTION`.
  События КПП читаются через существующее Web-подключение. Ошибка отдельного
  task-подключения не подменяется чтением другой БД. Таблицы задаются
  существующими `KPP_WAREHOUSE_TABLE` и `KPP_TASK_TABLE`.
- Журнал Reader задаётся существующим `KPP_RFID_TABLE` (dbo.RFID_Tags по умолчанию)
  и читается через Web-подключение к базе событий, без изменения аппаратного Reader.
- Только SELECT и локальные SET на отдельных `readonly=True`, autocommit
  соединениях, READ COMMITTED, lock timeout 2 с, query timeout 30 с.
  Существующий оперативный UI с READ UNCOMMITTED не меняется. Источники
  читаются последовательно; общей атомарной транзакции между БД нет.
- При ошибке SQL, неполном чтении, неверной серии или превышении защитного
  объёма отчёт не выдаётся. Пустая успешная выборка — нулевой отчёт, а не 100%.
  Пределы: 366 дней, 50 000 складских строк, 500 000 регистраций меток,
  200 000 событий, 100 000 сочетаний приёмка/метка для проверки Reader.
  Превышение — явная ошибка, а не обрезанная статистика. Ошибка или отсутствие
  проверки журнала Reader не превращаются в ноль чтений: окончательный Excel
  не выдаётся, а статус RFID-блока не показывается числом.
- `POST /api/efficiency-report` принимает `date_from`, `date_to`, опциональный
  boolean `include_details`; возвращает 202 и `job_id`. Короткий GET
  `/api/efficiency-report/<job_id>` сообщает pending/ready/error; готовый файл
  доступен по `/api/efficiency-report/<job_id>/download`. Все маршруты имеют
  ту же Basic Auth, что сайт. Задания не обращаются к LLM.
- Одновременно формируется одно задание на Web-узел, сохраняется не более
  восьми результатов на 15 минут. Excel, письмо и предпросмотр одного задания
  используют одну выборку, без повторного SQL. При HA-переключении/перезапуске
  Web временные результаты теряются; интерфейс предлагает сформировать заново.
- Фоновые задания нужны из-за 10-секундного upstream timeout Gateway на ub22.
  Менять Gateway, SQL-схему, установленные зависимости, Guardian, lease,
  очереди и работу считывателя для этой функции не требуется.
- Производственное подключение к SQL и появление кнопки на фактически
  работающем сайте должны быть проверены после принятия/развёртывания релиза.
  Локальные проверки не являются подтверждением заводской установки.

Изменения проходят отдельную ветку и PR/CI. Не выполнять `git pull` в рабочем
production-дереве. После принятия программного изменения используется штатное
обновление Guardian из main, сначала на резервах, с сохранением fencing,
rollback и текущих конфигураций. Операционные инструкции —
[OPERATIONS.md](../deploy/ha/OPERATIONS.md) и [RECOVERY.md](../deploy/ha/RECOVERY.md).
