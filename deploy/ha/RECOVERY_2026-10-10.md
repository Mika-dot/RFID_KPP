## Исправления

1. Пассивный Guardian после свежего успешного **пассивного** preflight
   (включая свободные порты и загрузку SDK) самостоятельно запускает обычную
   независимую проверку восстановления. SQL снимает fault только после
   непрерывного `verify_sec`. Нет зависимости от LLM/владельца controller.
   Живой owner, operator maintenance, работающие workers и проваленный
   candidate trial исключены. Повторные попытки ограничены durable cooldown
   300 секунд и repair-rate; рестарт агента его не сбрасывает.
2. После успешного deterministic repair LmRepair сразу уступает проверке
   Guardian; не ждёт модели и не перезапускает уже подготовленный резерв.
   Ответ 409 также не вызывает модель. При failed preflight diagnosis/LLM
   остаются доступными по прежнему каталогу.
3. `release_update.py --apply --recover-reserve` позволяет обновить только
   пассивный Perimetr/Comparator при нуле здоровых ведущих. Все три status
   должны быть свежими, protocol 2 и одного epoch, не более одного active.
   Atomic maintenance проверяет SQL lease перед остановкой. Физика, active
   резерв и `--handoff` в этом режиме запрещены. Никакой ручной очистки
   fault/election/lease или обхода preflight/qualification/rollback нет.
4. Проверен переход от **обеих фактически показанных версий**. У них нет
   установленного qualifier, поэтому работает предусмотренный fallback
   oracle нового инструмента. Выявлены три точных shadow differences:
   `warehouse_cannot_resolve_conflict.report_directions`: OUT → UNKNOWN;
   conflict count 0 → 1 у этого trace и `warehouse_later_nullable_tag`.
   Это исправление уже входящей в PR #9 ошибки смешения Warehouse OUT и
   направления прохода. Checked-in `guardian/legacy_shadow_allowlist.json`
   разрешает только эти old/new поля. Helper применяет его исключительно к
   указанным двум SHA с соответствующим Git tree и без tracked edits.
   Для неизвестного baseline остаётся zero-difference gate. Любой кандидат
   всё равно обязан совпасть со всеми 27 Golden expected outputs.
5. Исправлен новый review #9: report получает persisted WarehouseId links
   по дате Warehouse независимо от даты прохода. Link с adaptive delay
   свыше 24 часов сохраняет исходные EventId/VideoEventId, направление и
   conflict; не превращается в искусственную WAREHOUSE_ONLY строку.
   Pure union уже отдавал persisted link приоритет без временного ограничения;
   расширена именно SQL выборка. Неподтверждённое identity matching остаётся
   с прежним консервативным окном.

## Диагностика до изменения

Из отдельного clean checkout кандидата на Comparator/Perimetr:

```bash
sudo /opt/perimeter/venv/bin/python deploy/ha/diagnose_cluster.py --nodes-config /etc/perimeter/node.json --environment /etc/perimeter/environment
```

На ub22, если уже provisioned gateway config и monitor token:

```bash
sudo python3 deploy/ha/diagnose_cluster.py --nodes-config /etc/perimeter/gateway.json --token-file /etc/perimeter-ha-monitor.token
```

Вывод содержит версии, freshness, owner/repair/maintenance, failed preflight,
готовность пяти сервисов, failed dependencies и ограниченные numeric/bool
RFID latch/retry metrics. Credentials, тексты логов, events и данные людей
не выводятся. Выполняются только GET `/status`, SQL не вызывается. При
недоступности одного агента остальные всё равно опрашиваются.

## Выход из аварийного состояния

На **пассивном Comparator**, затем пассивном Perimetr, из checkout точного
SHA опубликованного PR #9:

```bash
PERIMETER_RELEASE=$(git rev-parse HEAD)
sudo /opt/perimeter/venv/bin/python deploy/ha/release_update.py --plan --release "$PERIMETER_RELEASE"
sudo /opt/perimeter/venv/bin/python deploy/ha/release_update.py --prepare --release "$PERIMETER_RELEASE"
sudo /opt/perimeter/venv/bin/python deploy/ha/release_update.py --apply --recover-reserve --release "$PERIMETER_RELEASE"
```

Каждый следующий узел сначала снова диагностировать: успешно восстановленный
Comparator может уже стать ведущим. Active VM нельзя обновлять с
`--recover-reserve`; обновить другой пассивный узел и использовать штатный
`--handoff`, как описано в основном runbook. Если все три agent недоступны,
inventory gate остаётся закрытым: нужен local native supervisor/log diagnosis,
а не ручной SQL grant. Если preflight не проходит, исправить его конкретную
причину; helper возвращает прошлую конфигурацию при неудачном apply.

После восстановления healthy owner и target-SHA резервов выполнить обычное
обновление физики с handoff, затем ub22 Web/Observer/dashboard и полный
GET-only verifier по [READY_TO_INSTALL_2026-10-09.md](READY_TO_INSTALL_2026-10-09.md).
Установка не выполняет проходов, отключений питания/сети или SQL migration.
SDK `UHFAPI.dll`, Wine на Linux и приоритет физика → Perimetr → Comparator
сохранены; выбор роли остаётся детерминированным.

Тесты проверяют исключение active/operator/trial/stale/SDK failure,
lease race, непрерывную проверку, durable cooldown, cold-start reserve
installation gates и отсутствие секретов в diagnosis. Квалификация старых
версий: 27 traces, 6 adapter contracts, 8 HA models; ровно 3 описанные
warehouse differences. Квалификация предыдущего подготовленного кандидата:
0 differences. Native SQL/SDK/factory acceptance требуют проверки на узлах.

Фактическая установка и восстановление заводского кластера из этой среды
не выполнены. Exact published SHA и Linux/Windows CI — в PR #9.
