## Выравнивание main и защита следующих обновлений

Код включает оба уже установленных RFID hotfix: независимая активность должна
быть позже последнего RFID-чтения; полная история видео может опровергнуть
старое основание latch без удаления latch и истории рестартов.

Для будущих кандидатов updater проверяет:

1. Existing main ancestry и прежний fencing protocol/epoch barrier.
2. `guardian/runtime_contract.json`: минимальная бизнес-генерация и обязательные
   capabilities. Принятый минимум хранится в durable `release.json` и растёт
   только после подтверждения релиза; неудачный trial может вернуться назад.
3. Шесть offline business-проверок из **установленного** checker. Изменение
   candidate-owned tests не может убрать эти проверки RFID causal/latch behavior.
4. Candidate regression suite и существующий preflight перед staging.

Отсутствующий контракт, пониженные возможности или провал защищённых проверок
дают durable quarantine exact SHA. Изменения только `.md`/`.rst`, либо идентичное
дерево, обновляют наблюдаемый main SHA, сохраняя runtime target равным текущему
runtime: нет staging, активации или HA переключения ради документации.
Скрипты, конфигурация и зависимости остаются runtime-изменениями независимо от папки.

Эти проверки защищают два конкретных hotfix; они не заменяют полную будущую
квалификацию всей бизнес-логики, golden replay и shadow-приёмку. Старый установленный
updater получает новую защиту только после принятия этого кода. Его установку,
restart/failback и автоматическое принятие нового SHA на заводе здесь не заявляем.
SQL migrations, grants, reset latch и изменения production-конфигурации не выполнялись.

`verify_live_rfid.py` по умолчанию ожидает заводской1c runtime, поддерживает
`--release EXACT_SHA` для следующего отдельно принятого релиза. Все read-only
SQL/SQLite, UUID/SENT/cursor, свежесть и epoch ограничения сохранены.
В этом раунде скрипт на заводе не запускался.

## Снимки YOLO в Web

Добавлены превью в колонку видео списка проходов и в HTML-предпросмотр отчёта;
клик открывает исходный снимок, карточка события показывает его целиком.
Отчёт теперь получает VideoEventId. Warehouse-only строке без видео не
приписывается ближайший чужой кадр.

HTTP /api/image/ID читает current ImageData и legacy ImageBase64, включая
бинарный JPEG и Base64 bytes/text. При повреждённом current поле применяется
валидный legacy снимок. MIME определяется по байтам, а не по историческому
ImageFormat. Поддержаны JPEG/PNG/GIF/WebP; авторизация остаётся общей с Web.
Источник учитывает KPP_VIDEO_TABLE / RFID_DB_LOG_TABLE.

Превью загружаются лениво; найденные снимки имеют private cache 300 секунд,
отсутствующие или повреждённые возвращают uncached 404. Проверки используют
настоящий Flask HTTP client с изолированным подставным DB cursor и не обращаются
к заводу. Отображение реальных production кадров после автообновления не наблюдалось.

## Ограничения, принятые пользователем

- Реальный power-off/network isolation physical и захват UHF/TCP резервом
  недоступны для испытания. Не выполнять fault injection и не считать остановку
  worker эквивалентом физического отказа. SQL fencing не разрывает TCP сам по себе.
- Архивная корреляция проведена без влияния на завод.
- Новые Zabbix items/triggers ранее пропущены по разрешению пользователя.
