# Стандарт отчёта эффективности КПП «Периметр»

Версия 1.3, формат от 26.10.2026. Это основной стандарт
периодического управленческого отчёта. Не возвращать в него все диагностические
листы прежней ручной сверки.

## Как пользоваться

На основном сайте `http://172.31.0.97:5051/` открыть **«Отчёт эффективности»**,
выбрать **«Дата от»** и **«Дата до (включительно)»**, нажать **«Сформировать
отчёт»**. После завершения доступны предпросмотр, **«Скачать Excel»** и
**«Скопировать письмо»**. Письмо копируется с таблицами, в том числе на
существующем HTTP Gateway; при запрете браузером доступен обычный текст.
Письмо автоматически никуда не отправляется.

По умолчанию включена подробная сверка. Основной лист **«Отчёт»** содержит:

1. Название и выбранный период, время МСК.
2. Два главных показателя: **«Периметр целиком»**, затем **«RFID-блок»**.
   Рядом с процентом всегда указаны числитель и знаменатель.
3. Таблица по дням и строка «Итого»:
   `Дата | Всего барабанов | С RFID | RFID считано | RFID KPI | Периметр целиком`.
4. Краткое объяснение учёта барабанов без зарегистрированной RFID-метки.
5. Количество барабанов с зарегистрированными метками без подтверждённого
   считывания. Список серий и технические причины — на опциональном листе сверки.
6. Готовый текст письма с темой, приветствием «Добрый день, Павел Валерьевич!»,
   двумя главными показателями и отдельным результатом распознавания полученных RFID. Письмо короткое: без дневной таблицы, сырых чтений, EPC/TID и списков серий. Не обещать будущую проверку,
   которую система сама не выполняет.
7. Короткая методика и время формирования для воспроизводимости результата.

Включённая по умолчанию галочка добавляет **«Сверку»** и **«Проверку катушек»**.
На «Сверке» — складские ID/даты, зарегистрированные и прочитанные полные метки,
ID исходных чтений и событий, факт распознавания Периметром, отдельно факт
привязки события к приёмке, история и результат проверки расхождения.

«Проверка катушек» содержит серии и ID всех позиций без меток 1С и с метками,
но без чтения в периоде. Люди заполняют причину, подтверждающий документ/журнал/фото,
ответственного, дату и комментарий. Изначально везде «Не проверено»; это
редактируемый Excel, заполненные причины обратно в БД автоматически не импортируются.
Снятие галочки даёт один основной лист. Полный поток изображений и чужие
RFID-метки в файл не включаются.

Оформление следует приложенному образцу: светлый фон, Carlito, тёмно-синий
заголовок `#16364D`, светло-синие шапки `#DFE8EF`, перенос длинного текста,
выделенная итоговая строка. Числа остаются числами; дневной и общий RFID KPI
и общие количества рассчитаны формулами с сохранёнными значениями. Нулевой
знаменатель — пустая процентная ячейка в Excel и «—» в предпросмотре/письме.

## Правила расчёта

**Эталон выборки — прямые записи адресного склада `dbo.Warehouse`** за период
`[начало первого дня; начало дня после последнего)`, а не количество строк
на экране сайта. Используются все строки, без лимитов пагинации Web.
Серия приводится к верхнему регистру, удаляются пробелы по краям и конечные
запятые/точки с запятой/точки (`4265/26,` → `4265/26`, `8975/26.` → `8975/26`). Разные непустые серии
не склеиваются, пустая серия вызывает ошибку, а не молчаливое исключение.

Единица отчёта — **уникальная серия барабана за выбранный период**.
Повторные строки склада и несколько меток одной серии не увеличивают число
барабанов. Дата — первая приёмка серии в периоде. Это отчёт о барабанах,
а не о количестве перемещений одной серии. Повторные приёмки одной серии
за другой период учитываются в соответствующем отчёте заново.

Серии с суффиксом `МК`/`MK` исключаются, как в согласованной сверке. В текущей
таблице Warehouse нет вида тары: отнесение остальных серий к барабанам
опирается на принятую номенклатуру учёта. Если в этот поток начнут поступать
бухты без отличимого суффикса, сначала нужен явный признак тары в источнике;
нельзя заявлять, что имеющиеся пять полей позволяют определить её физический вид.

| Колонка | Определение |
|---|---|
| Всего барабанов | Число уникальных серий складской выборки |
| С RFID | У серии есть хотя бы один непустой полный Tag в `dbo.RfidTags`, зарегистрированный не позже первой приёмки |
| RFID считано | Хотя бы один зарегистрированный полный Tag точно совпал с сырым чтением антенны за весь выбранный период |
| RFID KPI | `RFID считано / С RFID`; итог считается из сумм, а не как среднее дневных процентов |
| Периметр целиком | Число складских серий в объединённом учёте Периметра / всего складских серий |

Полный Tag — EPC вместе с TID, как в `RfidTags.Tag` и `KPP_ReelEvents.SourceTag`.
Совпадение только EPC-префикса недостаточно. Пробельное оформление полного
кода и регистр нормализуются. Несколько разных зарегистрированных меток одной
серии допустимы: достаточно одной считанной. Метка, зарегистрированная за
несколькими сериями, не доказывает обнаружение; это явно отмечается в отчёте.

**История реестра меток читается целиком до конца периода**. Не применять к
ней окно ±24 часа или 72-часовой cache агрегатора: регистрация может быть
за несколько месяцев до фактической приёмки. Метки, зарегистрированные после
приёмки, не увеличивают её исторический знаменатель.

**Основной KPI RFID-блока — сопоставление 1С с сырыми чтениями антенны**:
число уникальных барабанов выборки с хотя бы одной прочитанной зарегистрированной
меткой / число барабанов выборки с метками 1С. Чтения берутся только из
`dbo.RFID_Tags`. Наличие/отсутствие сеанса Aggregator, направление, WarehouseId,
привязка к видео и число повторов антенны не меняют этот KPI.

Время чтения — индексированный `RecordTime`. Штатный `SQLWriter` v4 сохраняет
в `RecordTime` и `SourceReaderTime` одно время захвата из spool, даже при
отложенной доставке; время вставки хранится отдельно в `ReceivedAt`. Это
проверяется регрессией SQLWriter на отложенной доставке. Для старых строк без SourceReaderTime
остаётся RecordTime. Не оборачивать индексируемую колонку в COALESCE: это
приводит к полному сканированию истории на каждом пакете меток. Если внешний
писатель изменит этот контракт, потребуется отдельное индексируемое поле
времени чтения; нельзя молча подменять время захвата временем доставки.
Сырые чтения проверяются **за весь выбранный период**
`[00:00 первого дня; 00:00 дня после последнего)`, а не в окне ±24 ч каждой
приёмки. Приёмка и чтение могут относиться к разным дням одного периода.
Дневная строка группируется по первой складской приёмке, а подтверждение
проверяется по всему периоду отчёта; это явно не дневная производительность антенны.
За пределами выбранного периода чтение не засчитывается.

Совпадение — точный нормализованный полный `EPC+TID`. SQL возвращает по каждой
метке число сырых чтений, первое/последнее время и min/max ID исходных строк.
Модуль расчёта повторно проверяет время и идентичность. Повторные приёмки
одной серии не размножают кандидатов и чтения.

Рядом с KPI выводятся: общее число сырых чтений за период; число чтений меток
отчётной выборки; количество уникальных меток 1С, найденных и ненайденных меток.
Так отдельно видны ответ «прочитана хотя бы одна метка барабана» и ответ
«прочитаны все зарегистрированные метки». Исторические дополнительные метки
из реестра могут уже не находиться на барабане; это не утверждение о поломке антенны.

`WAREHOUSE_ONLY` и `SUPERSEDED_BY_KPP` не являются подтверждением физического
считывания, даже если в строку скопирован Tag из 1С. Само присутствие серии
на сайте и наличие Warehouse-записи не доказывают чтение антеннами.

Только диагностическое сопоставление Aggregator с приёмкой (не влияет на KPI антенны):

1. Сохранённый `WarehouseId` — приоритетный, в том числе при задержке больше
   суток. Tag всё равно обязан совпадать с реестром этой серии.
2. Для ещё не связанного события — точный полный Tag из реестра серии в
   пределах ±24 ч от приёмки, с исключением известного возврата `IN`.
3. Событие, уже связанное с другой Warehouse-записью, не перехватывается.

Это отдельная отчётная проекция, а не изменение алгоритма идентификации
агрегатора `TAG → IDS → однозначный SERIES`. Исторические метки одной серии
не должны искусственно превращаться в «неоднозначную серию» для этого KPI.

`Периметр целиком` включает прямые Warehouse-записи по существующему
контракту `RFID КПП ∪ адресный склад`. Поэтому при доступном и полном чтении
складской выборки этот показатель равен 100%; он не является независимой
проверкой антенн или полноты внешнего обмена 1С со складской SQL-таблицей.

Регистрация в 1С не гарантирует, что физическая метка сохранилась на барабане.
Стандартная формулировка расхождения: «считывание не подтверждено у барабана
с зарегистрированной меткой», а не безусловное «антенна неисправна».

## История контрольного примера и границы проверки

Исходная ручная сверка 19–22.10.2026 содержала следующие значения:

| Дата | Всего | С RFID | Считано | RFID KPI | Периметр целиком |
|---|---:|---:|---:|---:|---:|
| 19.10 | 24 | 1 | 0 | 0% | 24/24 |
| 20.10 | 34 | 24 | 24 | 100% | 34/34 |
| 21.10 | 40 | 24 | 24 | 100% | 40/40 |
| 22.10 | 33 | 32 | 32 | 100% | 33/33 |
| Итого | 131 | 81 | 80 | 98,77% | 131/131 = 100% |

Эти числа являются историей ручной сверки, **а не доказанным эталоном физической
работы Reader**: старый экспорт проходов мог помещать Tag из 1С в Warehouse-only
строку с нулевым RfidReadCount. Поэтому воспроизведение этих чисел из прежнего
Excel проверяло арифметику и сопоставление меток, но не физическое считывание.
Нельзя подставлять 98,77% в новый отчёт как константу или исключать серии ради
достижения этого процента.

Новая заводская выгрузка v1.0 содержала 134/83/36; она читала только события
Aggregator и не проверяла исходный журнал Reader. Эти 43,37% также нельзя
автоматически считать окончательной эффективностью RFID-блока. В новой выборке
есть дополнительные серии 8843/26, 8844/26, 8652/26; их наличие требует сверки
складских источников, а не жёсткого исключения из кода. 4265/26 в новой выгрузке
имеет подтверждение событием 75074, в отличие от прежней ручной сверки.

Заводская выгрузка v1.1 за 19–23.10.2026 дала 49/112 = 43,75%, но не содержит
построчной сверки и сырых исходных чтений. По одному этому Excel нельзя установить,
какие метки и времена не попали в числитель. Кроме того, это пять дней, тогда
как исходная ручная сверка 98,77% относилась к четырём дням (19–22 октября).
В v1.1 оставалось окно ±24 ч приёмки и объединение с Aggregator. Версия 1.2
проверяет сырые чтения за выбранный период. Проверка полного архива БД от
26.10 подтвердила за 19–23 октября те же 49/112, а за 19–22 октября — 41/83:
ограничение окна в этих конкретных данных не объясняло низкий результат.

Синтетические регрессии проверяют: 80 барабанов с сырыми чтениями из 81 дают
98,77% независимо от числа событий Aggregator; реальное чтение в другом дне
выбранного периода засчитывается без сессии; миллион повторов одной метки не
заменяет остальные барабаны; историческое чтение вне периода не засчитывается.
Эти примеры не являются реальными результатами завода. Реальные EPC в тестах
не публикуются.

## Контроль обработки и распределение причин (v1.3)

Основные показатели нельзя смешивать:

- **Периметр целиком**: учёт `RFID КПП ∪ адресный склад`.
- **RFID КПП**: катушки с точным сырым чтением / катушки с метками 1С.
- **Распознавание полученных RFID Периметром**: катушки с сырым чтением,
  у которых есть физическое событие `IsReel=1`, / катушки с сырым чтением.
  Точное совпадение метки обязательно. Направление и WarehouseId не являются
  условиями распознавания: они относятся к отдельной связи с приёмкой.
  Сеанс может начаться до периода: учитывается пересечение FirstSeen–LastSeen
  с выбранными датами, включая длинные сеансы старше окна складского fallback.
- **Прохождение входящего потока**: фактическое число строк периода с
  `Id <= LAST_RFID_ID_V3` / число строк периода. Это не расстояние между ID,
  не оценка доступности сети и не доказательство отсутствия всех ошибок ПО.
- **Ошибки обработки**: число записей и незакрытых записей
  `KPP_ProcessingErrors` за период. Ноль записей не означает, что все виды багов исключены.
- **Коммуникации**: без временной истории сетевых инцидентов процент доступности
  и долю вызванных сетью пропусков не вычислять. Текущая lease/heartbeat не доказывает
  доступность за прошлую неделю. `LAST_RFID_ID_V3` не доказывает, что считыватель
  получил все физические метки до доставки в SQL.
- **1С / человеческий фактор**: отсутствие зарегистрированной метки — факт данных,
  а не доказанная ошибка человека или отсутствие наклейки. Неотправленный из 1С
  документ невозможно посчитать без независимого исходящего журнала/эталона 1С.

Для непрочитанных барабанов автоматически проверяется доступная история:
точные чтения вне периода; только EPC без полного TID; отсутствие полного
совпадения; неоднозначная метка; либо «история не проверена». Поиск истории
использует существующий индекс EPC и точный TID для формата EPC24+TID24.
Другие форматы не объявляются отсутствующими. Ошибка/лимит диагностики отображаются
явно и не подменяются нулём. Если во время проверки истории появилось точное
чтение периода, противоречащее числителю, отчёт отклоняется и требует повторного формирования.

Контроль архива 26.10 за 19–23.10: 167 катушек в учёте; 112 с метками;
49 имеют сырые чтения, у 48 есть распознанные события катушек; одна серия
4265/26 имеет событие 75074 с IsReel=0 / NOT_CONFIRMED.
Периметр целиком — 167/167; распознавание поступивших RFID — 48/49 = 97,96%.
Наличие физического события само по себе не равно успешному распознаванию.
Нераспознанная серия включается в лист проверки даже при наличии сырого чтения.
Из 63 без точного чтения периода: 51 не имеют точного совпадения в доступной
истории, у шести встречается только EPC в периоде, ещё у шести точные чтения
за пределами периода. Зарегистрированных ошибок обработки в выгрузке нет.
В доступных таблицах нет достаточной истории для распределения этих случаев
между сетью, физическим оборудованием и действиями людей.

Автоматическое формирование выполняет обычный Python/SQL-код, без GPT.
Лог Web фиксирует период, итоговые количества, статус истории, длительность
и класс ошибки источника. Строки подключения, тексты ODBC-ошибок, пароли,
полные метки и токен скачивания в эти сообщения не попадают. Guardian сохраняет
вывод Web в штатном логе дочернего процесса; файловые логи Reader/Guardian
автоматически не читаются из Web и не считаются просмотренными.

## Источники, сервер и границы

- Реализация: `common/efficiency_report.py` — единая расчётная логика и письмо;
  `common/efficiency_xlsx.py` — Excel; `web/efficiency_api.py` — SQL и задания;
  `web/efficiency_ui.py` — диалог. Подключение — production wrapper
  `web/kpp_reel_dashboard_v3_fixed.py`. Старая выгрузка проходов сохранена.
- Warehouse и RfidTags читаются через существующий `KPP_TASK_CONN_STR`, если
  он задан; иначе через `KPP_WEB_DB_CONNECTION`/`RFID_DB_CONNECTION`.
  События КПП читаются через существующее Web-подключение. Ошибка отдельного
  task-подключения не подменяется чтением другой БД. Таблицы задаются
  существующими `KPP_WAREHOUSE_TABLE` и `KPP_TASK_TABLE`.
- Журнал Reader задаётся существующим `KPP_RFID_TABLE` (dbo.RFID_Tags по умолчанию)
  и читается через `RFID_DB_CONNECTION`, используемый аппаратным Reader; при отсутствии отдельной строки — через Web-подключение. Подключения только для чтения, аппаратный Reader не меняется.
- Только SELECT и локальные SET на отдельных `readonly=True`, autocommit
  соединениях, READ COMMITTED, lock timeout 2 с, query timeout 30 с.
  Существующий оперативный UI с READ UNCOMMITTED не меняется. Источники
  читаются последовательно; общей атомарной транзакции между БД нет.
- При ошибке SQL, неполном чтении, неверной серии или превышении защитного
  объёма отчёт не выдаётся. Пустая успешная выборка — нулевой отчёт, а не 100%.
  Пределы: 366 дней, 50 000 складских строк, 500 000 регистраций меток,
  200 000 событий, 100 000 уникальных меток для проверки Reader.
  Превышение — явная ошибка, а не обрезанная статистика. Ошибка или отсутствие
  проверки журнала Reader не превращаются в ноль чтений: окончательный Excel
  не выдаётся, а статус RFID-блока не показывается числом.
- `POST /api/efficiency-report` принимает `date_from`, `date_to`, опциональный
  boolean `include_details`; возвращает 202 и `job_id`. Короткий GET
  `/api/efficiency-report/<job_id>` сообщает pending/ready/error; готовый файл
  доступен по `/api/efficiency-report/<job_id>/download`. Все маршруты имеют
  ту же Basic Auth, что сайт. Задания не обращаются к LLM.
- Одновременно формируется одно задание на Web-узел, сохраняется не более
  восьми результатов на 15 минут. Excel, письмо и предпросмотр одного задания
  используют одну выборку, без повторного SQL. При HA-переключении/перезапуске
  Web временные результаты теряются; интерфейс предлагает сформировать заново.
- Фоновые задания нужны из-за 10-секундного upstream timeout Gateway на ub22.
  Менять Gateway, SQL-схему, установленные зависимости, Guardian, lease,
  очереди и работу считывателя для этой функции не требуется.
- Производственное подключение к SQL и появление кнопки на фактически
  работающем сайте должны быть проверены после принятия/развёртывания релиза.
  Локальные проверки не являются подтверждением заводской установки.

Изменения проходят отдельную ветку и PR/CI. Не выполнять `git pull` в рабочем
production-дереве. После принятия программного изменения используется штатное
обновление Guardian из main, сначала на резервах, с сохранением fencing,
rollback и текущих конфигураций. Операционные инструкции —
[OPERATIONS.md](../deploy/ha/OPERATIONS.md) и [RECOVERY.md](../deploy/ha/RECOVERY.md).

```bash
python tools/audit_efficiency_exports.py --data-dir /private/csv --date-from 2026-10-19 --date-to 2026-10-23 --xlsx audit.xlsx --json audit.json
```

Имена — `Таблица_YYYYMMDDHHMM.csv`; старые PreV3 backup не подменяют актуальную

RuntimeState используются при наличии и помечаются как непроверенные при отсутствии.
Этот инструмент не подключается к SQL и не изменяет производственную БД.
Приватные CSV/JSON и реальные полные метки в Git не коммитить.

### Доставка Reader → SQL

Отдельная проверка использует ReceivedAt, SourceReaderTime и TimeQuality.
Доля строк не позже контрольных 120 секунд рассчитывается только по пригодным
меткам HOST_CAPTURE_TIME / APPROXIMATE_AFTER_RECONNECT с неотрицательной задержкой.
LEGACY_RECORD_TIME не считается независимым измерением доставки. Выводятся число
задержанных строк, приблизительная максимальная задержка в целых секундах,
число записей после переподключения и число строк без пригодных временных меток.
Это не процент доступности сети: задержка также включает очереди, запись SQL и
погрешность часов, а отсутствие физического чтения по этим полям не измеряется.

Архив 26.10 за 19–23 октября: 12092 пригодных временных метки, 114 доставок
позже 120 секунд, 11978/12092 = 99,06% в пределах порога. Максимум около 5039 с;
292 записи имеют APPROXIMATE_AFTER_RECONNECT. Эти факты не распределяют 63
непрочитанные катушки между сетью и другими причинами.
